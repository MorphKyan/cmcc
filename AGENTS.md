# Repository guidance

CMCC exhibition-hall assistant: a FastAPI backend converts speech/text into structured device commands through ASR, RAG and LLM processing; `frontend/` contains the Vue app and embeddable widget.

## Scope and completion

For implementation requests, proceed through safe local edits, relevant validation, fixes for failures caused by the change, and affected reruns without additional approval. Completion means the requested behavior is implemented and relevant failures are resolved, or a concrete external blocker is reported. Stop expanding validation once the affected checks pass unless new evidence warrants more.

Live exhibition-device commands, production deployment, overwriting operational data, credential/certificate changes, and paid external calls require authorization covering that operation. Existing authorization is sufficient. Local code and deployment-file edits do not themselves require approval. Do not automatically commit changes or add author/sign-off attribution.

## Project constraints

- Pipelines live in `src/services/audio_pipeline.py` and `text_pipeline.py`; shared processors are wired through `src/core/dependencies.py` and `lifespan.py`. Preserve asynchronous processor initialization so model loading does not block startup.
- CSV knowledge is managed by `src/services/data_service.py`; `data/` contains operational knowledge, while `chroma_db/` is a generated embedding store. Use disposable paths for test data and indexes; do not treat the working database as scratch space.
- Device, media, door and area names in commands must match the knowledge base. Preserve the command schemas and validation in `src/module/llm/tool/definitions.py`. In the existing `open_media` contract, `device` identifies the media and `value` identifies the target device.
- LLM/RAG provider aliases include `openai_compatible`, `openai`, `siliconflow`, and `modelscope`. The `modelscope` provider still uses legacy `modelscope_*` settings; preserve that compatibility, including single-item embedding batches (see `test/unit/test_openai_compatible_legacy_config.py`). Ollama uses `ollama_model`.
- Microphone and Ollama support are optional: `ENABLE_MIC_INPUT=true` / `ENABLE_OLLAMA=true` and their corresponding dependencies enable them. Keep base installations usable without those extras.
- Python 3.12 is the minimum supported version and the Docker/Conda runtime baseline. Prefer built-in collection annotations (`list`, `dict`, `set`, `tuple`).
- `frontend/dist-widget/` is generated by `npm run build:widget`; edit `frontend/src/` or `frontend/public/` and rebuild when artifact updates are in scope.

## Configuration and local commands

Run backend commands from the repository root using `.venv/bin/python` (Windows: `.venv\Scripts\python.exe`); shell activation is optional.

- Start locally: `.venv/bin/python main.py --host 127.0.0.1 --port 8000`. The backend serves HTTP; nginx terminates HTTPS/WSS. There are no backend SSL CLI flags. Health is `/api/`; `/` redirects to `/docs`.
- Local unit tests: `.venv/bin/python -m pytest test/unit`; select affected files as appropriate. `test/api/` has mocked data/RAG fixtures. `test/rag/` uses live DashScope calls when `DASHSCOPE_API_KEY` is set. `tests/` mixes service, model-download, TTS and AEP/device scripts, some with import-time side effects; it is not an offline regression suite.
- Frontend commands run in `frontend/`: `npm run dev`, `npm run build`, or `npm run build:widget`. `VITE_BACKEND_URL` sets the client API base (default `/api`); `VITE_PROXY_TARGET` sets the development proxy (default `http://127.0.0.1:8000`).

Configuration loading is defined in `src/config/config.py`: explicit path, then `CONFIG_FILE`, then `config/config.toml`, then `config/config.example.toml`, then defaults. The tracked templates are actually `config/config.dev.example.toml` and `config/config.prod.example.toml`; select one explicitly with `CONFIG_FILE` or copy it to the local `config/config.toml`. Put local credentials in local configuration, not source defaults or tracked examples.
